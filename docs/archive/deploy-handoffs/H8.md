## Decisiones tomadas
- Default `"restore"`: conserva el comportamiento actual del LED virtual (no rompe
  nada) y deja `"safe"`/`"off"` como opt-in para cuando existan actuadores físicos.
- `"safe"` se implementa reutilizando `_load_led_pin()`: el LED virtual tiene
  `pin: null`, por lo que `_load_led_pin()` devuelve `0` y se restaura; un pin físico
  devuelve un BCM `> 0` y se fuerza `False`. Así no se duplica la fuente de verdad de
  `devices.yaml`.
- La política se encapsula en `_apply_startup_policy()` (método estático puro) para
  mantener `restore_from_db()` legible y facilitar el test unitario.

## Riesgos / pendientes
- `"safe"` depende de que `_load_led_pin()` devuelva `0` para dispositivos virtuales.
  Si en el futuro se configura un LED físico, `"safe"` lo apagará al arrancar (comportamiento
  deseado); validar el flujo completo con hardware real (marcado HIL).
- `state_manager.py` importa el singleton `settings` a nivel de módulo; los tests mutan
  ese objeto compartido vía `monkeypatch`, que lo restaura al finalizar cada test.
- Los 5 warnings de pytest son preexistentes (patrón `AsyncMock` en el stub de
  persistencia); no se abordaron por quedar fuera del alcance H8.
