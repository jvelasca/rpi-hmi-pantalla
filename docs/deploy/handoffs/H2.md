# Handoff H2 — Endurecer display y touch

## Resultado
Completado (no parcial). Cuatro cambios independientes en `display/` para
endurecer el display y el driver táctil:

1. `Screen.allow_mock_fallback` ahora por defecto `False` (antes `True`). En
   producción (`display/app.py`) ya se construye `Screen(..., allow_mock_fallback=mock)`,
   por lo que sin `--mock` un fallo de DRM ya no cae silenciosamente a mock.
2. `TouchHandler.raw_to_screen()` aplica `invert_x`/`invert_y` (antes código
   muerto). La inversión se aplica tras la transformación afín y antes del
   clamp final a `[0, width-1]`/`[0, height-1]`.
3. `TouchHandler.__init__` lee los límites reales de `ABS_X`/`ABS_Y` del
   dispositivo evdev vía `EVIOCGABS` (ioctl) con un helper defensivo
   `_read_abs_max(device_path, axis) -> int | None`. En Windows (sin `fcntl`)
   o ante cualquier fallo, cae al fallback `RAW_MAX = 4096`.
4. `HeaderWidget` en `_create_widgets()` usa `version="0.3.0"` (antes `"v1.2"`),
   alineado con el resto del proyecto.

Tests: `test_mapping_with_invert` revertido para comprobar coordenadas
invertidas; añadida la clase `TestReadAbsMax` (4 tests) que cubre el fallback
del helper (sin hardware, sin `fcntl`, dispositivo inexistente y fallback a
`RAW_MAX` en `__init__`).

## Decisiones tomadas
- **Constante `EVIOCGABS` corregida.** La fórmula del enunciado
  `(2 << 30) | (0x40 << 16) | (0x03 << 8) | axis` es incorrecta. La correcta
  para `_IOR('E', 0x40 + axis, struct input_absinfo)` es
  `(2 << 30) | (0x45 << 8) | (0x40 + axis) | (24 << 16)`
  (`dir=2<<30`, `type='E'=0x45<<8`, `nr=0x40+axis`, `size=24<<16`).
  Para `ABS_X` da `0x80184540`, valor canónico de `EVIOCGABS(ABS_X)`.
  `struct input_absinfo` = `"iiiiii"` (6 ints = 24 bytes).
- El import de `fcntl` es **diferido dentro de `_read_abs_max`** para no romper
  el arranque en Windows. Todo va en `try/except (ImportError, OSError, ValueError, struct.error)`
  devolviendo `None`.
- `touch_max_x`/`touch_max_y` pasaron de `int = RAW_MAX` a `int | None = None`
  para poder distinguir "no se pasó explícitamente" (→ leer del device) de un
  valor forzado por el llamante. El fallback sigue siendo `RAW_MAX`.
- El device se resuelve **una sola vez** en `__init__` (`resolved_path =
  device_path or _find_touch_device()`), se usa para leer límites y se pasa a
  `_init_device`, que ya **no re-ejecuta** `_find_touch_device()` (evita doble
  escaneo de sysfs y doble warning). `_init_device` es privado y solo se llama
  desde `__init__`.
- La inversión se aplica sobre el float afín (`sx = screen_width - 1 - sx`)
  antes del `round`+clamp; es equivalente a invertir el valor redondeado
  (`round(W-1-f) == W-1-round(f)` para `W` entero).
- `test_no_fcntl_returns_none` fuerza el `ImportError` con
  `patch.dict(sys.modules, {"fcntl": None})`, lo que lo hace determinista
  también en Linux (no depende del SO real).

## Riesgos / pendientes
- La ruta del ioctl real (`EVIOCGABS`) **no se puede validar en Windows** (no
  hay `fcntl` ni hardware evdev). Si en la Pi el ioctl/estructura fuera
  incorrecto, `_read_abs_max` devolvería `None` y se usaría `RAW_MAX` (sin
  crash), pero conviene un smoke en hardware para confirmar que se lee el
  `maximum` real del panel XPT2046 (típicamente 4095, no 4096).
- Si el panel reporta un `maximum` distinto de 4096, el mapeo afín por defecto
  cambia. Los sistemas ya **calibrados** no se ven afectados porque
  `_load_calibration()` sobrescribe los coeficientes por defecto.
- `_init_device` ya no auto-detecta cuando recibe `None`. Es un método privado
  sin llamantes externos; si en el futuro se invocara directamente con `None`,
  no detectaría el dispositivo (debe pasarse la ruta resuelta).
- El `version` del `HeaderWidget` queda `"0.3.0"`; el default del widget sigue
  siendo `"v2.0"` (solo se cambió la llamada de `display/app.py`).
